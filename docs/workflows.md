# Workflows: the roles a repo's pipeline runs

A workflow names the roles that work on a task in one repo, in order. Each role has a task class, its own instructions, and optionally a profile it is pinned to. The declaration lives in `.ag/workflows/<name>.yaml`, next to the rest of the repo's context, and it is committed with the repo.

Workflows are optional. A repo with no `.ag/workflows/` folder runs tasks exactly as before.

## The file

```yaml
# Plan, implement, test and review, each by its own role. `agn sync` compiles this file into
# Claude Code's .claude/agents/ and .claude/commands/; edit here and run `agn sync` again.
name: tiered
description: Plan, implement, test and review, each by its own role.
roles:
  - name: architect
    class: research
    instructions: |
      Turn the task into a short plan: goal, files, signatures, acceptance criteria, out of scope.
      Write no code. Stop and ask when a choice changes an interface, a schema or a dependency.
  - name: developer
    class: implement
    instructions: |
      Implement the architect's plan. Run and test as you go. Report the files touched,
      deviations from the plan and why, and risks for review. No pasted logs.
  - name: test-writer
    class: implement
    instructions: |
      Write unit tests for the developer's change: one per acceptance criterion in the plan,
      plus one for each bug you find. Change no production code; report gaps instead.
  - name: reviewer
    class: review
    # Pin a profile on another harness than the developer's, so the review is independent:
    # profile: codex:default:native
    instructions: |
      Review the diff against the plan: correctness, size, naming, tests that exercise the
      change. Report findings with file and line. Change nothing.
```

## Every key

| Key | Required | What it is |
|---|---|---|
| `name` | yes | The workflow's name. It must equal the file's own name without `.yaml`: one workflow, one file, one `/<name>` command. Lowercase letters, digits and dashes, starting with a letter |
| `description` | no | One line, for `agn workflow list` |
| `roles` | yes | At least one role, in the order they run |
| `roles[].name` | yes | The role's name, under the same rule as `name`. Two roles cannot share one |
| `roles[].class` | yes | What the role's work is: `implement`, `debug`, `refactor`, `review`, `research`, `ui` or `general`. It is what agn uses to pick a model for the role |
| `roles[].profile` | no | A profile id such as `codex:default:native`, pinning the role to one agent and model. Absent, agn picks per class from your profiles when the workflow is compiled |
| `roles[].instructions` | no | What to tell this role, and only this role. `.ag/instructions.md` still applies to all of them |

A key the schema does not know is an error, not a comment: `agn` names the file and the key and stops.

## Writing one

```
agn workflow init                                   # .ag/workflows/tiered.yaml
agn workflow init --template single --name dev       # .ag/workflows/dev.yaml
agn workflow init --template none
```

`--template` chooses what is written:

| Template | What it writes |
|---|---|
| `tiered` | The four roles above: architect, developer, test-writer, reviewer. The default |
| `single` | One `developer` role that implements, tests and reports |
| `none` | Nothing. The repo keeps running tasks as it does today |

`--name <n>` names the workflow and its file; it defaults to the template's own name. `--force` overwrites a file that is already there; without it, `agn workflow init` refuses rather than replace what you wrote. `--repo <r>` acts on a repo other than the one you are in, and always on its registered checkout rather than a task worktree.

The templates are text with comments, including a commented-out `profile:` line. Uncomment it to pin a role.

## Reading them back

```
agn workflow list
agn workflow show tiered
```

`list` prints one row per workflow with its roles in order. `show` prints the workflow's fields and then each role: its number, name, class, the profile it is pinned to or `agn picks at sync`, and its instructions. Both take `--repo <r>` and `--json`.

## What `agn sync` writes

`agn sync` compiles every workflow under `.ag/workflows/` into Claude Code's own files. Each role becomes a subagent, and each workflow becomes a slash command that runs the roles in order.

For the tiered workflow above, with `architect` resolved to `claude-code:fable:native`, `developer` to `claude-code:opus:native`, `test-writer` to `claude-code:sonnet:native`, and `reviewer` pinned to `codex:default:native`:

`.claude/agents/architect.md`

```
---
name: architect
description: The architect role of the tiered workflow (research).
model: fable
---
<!-- generated by agn sync from .ag/workflows/tiered.yaml; edit that file, not this one -->

Turn the task into a short plan: goal, files, signatures, acceptance criteria, out of scope.
Write no code. Stop and ask when a choice changes an interface, a schema or a dependency.
```

`.claude/commands/tiered.md`

```
---
description: Plan, implement, test and review, each by its own role.
argument-hint: <task>
---
<!-- generated by agn sync from .ag/workflows/tiered.yaml; edit that file, not this one -->

Run the tiered workflow for: $ARGUMENTS

Do the steps in order. Do no step's work yourself. Give each step the task and the reports of the steps before it.

1. architect (claude-code:fable:native): use the architect subagent.
2. developer (claude-code:opus:native): use the developer subagent.
3. test-writer (claude-code:sonnet:native): use the test-writer subagent.
4. reviewer (codex:default:native, another agent): run `agn handoff --to codex:default:native` (or the agn_handoff MCP tool) with a note that carries the reviewer instructions below, what the steps above did, and the steps that remain. The handoff ends this session; the next agent continues from the note.
   Reviewer instructions:
     Review the diff against the plan: correctness, size, naming, tests that exercise the
     change. Report findings with file and line. Change nothing.

When the last step is done, report each step's result in one line, then the last report in full.
```

`model` is the model segment of the profile the role resolved to, in the words Claude Code's own `model:` field takes: `fable`, `opus`, `sonnet`, `haiku` or a full model name. A profile with no model segment, such as `claude-code:default:native`, writes `model: inherit`, and the role runs on whatever model the session is already on. The command's `description` is the workflow's, or the role names when the file has none.

A role on another agent - Codex, Pi, OpenCode, anything but Claude Code - has no subagent file. Its step runs `agn handoff --to <profile>` instead. The handoff ends the Claude Code session and starts the next agent in the same worktree, with a note carrying that role's instructions, what the earlier steps did, and the steps that remain.

Claude Code runs the steps. agn compiles the files and starts nothing: no stage transitions, no retries, no failure handling. If a step fails, the session says so and you decide.

## What `agn sync` reports

```
wrote .claude/agents/architect.md
wrote .claude/commands/tiered.md
tiered/architect: claude-code:fable:native (recommended for research)
tiered/reviewer: codex:default:native (pinned)
```

One line per role, after the files. `pinned` is the `profile:` the workflow file names. `recommended for <class>` is the recommender's pick for a role with no pin, made from the profiles available on this machine when the sync ran. `replaced` is a pin agn could not use:

```
tiered/reviewer: claude-code:opus:native (pin codex:default:native replaced: codex:default:native is not a profile on this machine; recommended for review)
```

A pin is replaced for one of two reasons only: no profile on this machine has that id, or the profile is there and not available - not logged in, or its key is missing. A cost ceiling never replaces a pin; a run past its budget is refused at run time instead.

Because the recommender reads what is available now, two syncs on different days can write different models for the same role. Pin the role to fix it.

## Committing the generated files

Commit `.claude/agents/` and `.claude/commands/` with the workflow file. A task's worktree is cut from a commit, so those files are what the agent in it reads. A launch compiles them again from the worktree's own committed workflow files, so a pin that is unavailable right now is replaced before the agent starts.

The header on the first line under the front matter is how agn knows the file is its own. A file without it is one you wrote, so sync stops, names it, and writes nothing - the same rule as `CLAUDE.md` and `AGENTS.md` (see [project context](project-context.md)). Merge what you want to keep into the workflow file, then run `agn sync --force`.

Rename or delete a role and the agent file it used to write stays where it is: agn does not remove files it no longer generates. Delete it yourself.
